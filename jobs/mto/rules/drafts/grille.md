# Grille Schedule Rule

>
> This rule has been reconciled against the current `Grille Schedule.xlsx` template and against one real project Lisp export workflow supplied by the user. The source lifecycle is known: the user keeps one current export file in WIP, deletes the old export when the drawing changes, and exports a replacement before asking MTO to update the schedule.

## Source model

Use `rules/_common/drawing-export-driven.md`.

The drawing-export source model itself is operational. This grille rule remains draft only because some field-level semantics and deterministic merge details still need further project validation.

Primary project source: the **single current WIP Excel/CSV export** generated by the project Lisp from grille block attributes in the completed design drawing.

Operational source discovery:

- use the current grille export explicitly identified/provided by the user while the Lisp still has the legacy project-name filename bug;
- after the Lisp naming fix, resolve the canonical schedule-specific export;
- do not resolve `latest` by timestamp or filename;
- the user is responsible for deleting the previous export and generating the current one when the drawing changes.

Optional supplement: matching grille technical data under `00 Input/.../grille/` when useful and sufficiently exact. Absence of useful grille technical data is acceptable and common.

## Template authority

The current workbook is `Grille Schedule.xlsx`.

Preserve the workbook's existing two-row header structure and order exactly. The current template fields are:

1. `REF. NO.`
2. `MAKE`
3. `MODEL`
4. `AIR TYPE`
5. `DESIGN` with subheader `AIR FLOW L/s`
6. `NECK SIZE` with subheader `L x W mm`
7. `FACE SIZE` with subheader `L x W mm`
8. `FLEX DUCT` with subheader `Dia mm`
9. `GRILLE TYPE`
10. `COLOR`
11. `CUSHION HEAD` with subheader `HEIGHT mm`
12. `DAMPER TYPE`
13. `SYSTEM`
14. `COMMENTS`

Do not rename `DESIGN` to `AIR FLOW` in the workbook. `DESIGN / AIR FLOW L/s` is one schedule field whose semantic value is design airflow.

## Initial vs update behavior

Do not apply the old rule `CLEAR TEMPLATE BEFORE FILL` to a live schedule.

- If no live grille schedule exists: copy the read-only template, clear sample data rows only, and populate the new live schedule.
- If a live grille schedule already exists: reconcile/update it from the single current WIP export by stable grille identity.
- Do not modify template headers, merges, formatting, borders, comments, or column order.
- Whether a row that disappears from the replacement export should be removed or retained/flagged is still **TBC from real implementation**; do not invent that behavior yet.

## Source priority

For each field:

1. explicit user instruction for the current run;
2. project-specific grille rule/override;
3. current WIP Lisp export from the design drawing;
4. exact-match technical data from `00 Input` only to fill missing fields;
5. `-` when unsupported.

Never let generic manufacturer data overwrite an explicit drawing-export/project value.

## Field semantics

### REF. NO.

- Primary: explicit grille/block tag from the WIP Lisp export.
- Do not invent or renumber tags.
- This is the preferred stable row identity candidate, pending duplicate-tag validation on a real raw export.

### MAKE

- Use explicit project/vendor/manufacturer data when available.
- If not available, use `-`.
- Missing MAKE is not by itself a run failure.

### MODEL

- Use exact matching model information when available.
- If not available, use `-`.
- Do not infer model from grille type or size.

### AIR TYPE

Normalize only from an explicit source value or an approved project rule.

Accepted candidate normalization:

- `SA` / `S` -> `SUPPLY`
- `RA` / `R` -> `RETURN`
- `EA` / `E` -> `EXHAUST`
- `OA` / `O` -> `OUTSIDE AIR`
- `TA` / `T` -> `TRANSFER`

Do **not** derive AIR TYPE from the REF. NO. prefix unless the project explicitly confirms that naming convention.

### DESIGN / AIR FLOW L/s

- Semantic: design airflow for the grille, in L/s.
- Current WIP drawing export is primary.
- If the template unit already specifies L/s, write the numeric value only.
- Deterministic unit conversion may be used only when source units are explicit.
- Missing airflow -> `-`.

### NECK SIZE

- Semantic: duct/grille neck connection size.
- Preserve template convention `L x W`.
- Reorder only when the source explicitly identifies the source dimension axes/order.
- Do not infer face size from neck size or vice versa.

### FACE SIZE

- Semantic: visible grille face size.
- Preserve template convention `L x W`.
- May legitimately be `-` for grille types where no separate face-size field applies or no evidence exists.
- Do not derive from neck size without an explicit project/manufacturer rule.

### FLEX DUCT

- Template semantic: flexible-duct diameter, with unit provided by subheader `Dia mm`.
- Prefer numeric diameter only when writing into the template data cell (for example `200`), because the template carries the unit/context.
- Do **not** automatically append `Dia` into the cell unless real implementation confirms that convention.
- `-` when not applicable or unsupported.

### GRILLE TYPE

- Use explicit block attribute/project selection/technical-data type.
- Examples observed in the current template include `EGGCRATE`, `WEATHER PROOF LOUVRE`, `SIDE BLOW`, `4-WAY LOUVRE FACE`, `3-WAY LOUVRE FACE`, and `HALF CHEVRON`.
- Do not classify grille type from tag alone.

### COLOR

- Use explicit WIP/project/architectural information.
- Current template examples include both `WHITE` and `ARCHITECT`; therefore **do not default every missing/unclear color to `ARCHITECT`**.
- Missing unsupported color -> `-` unless a project-specific rule establishes another default.

### CUSHION HEAD

- Semantic: plenum/cushion-head height.
- Template subheader already provides `HEIGHT mm`.
- Current template cells include text such as `350mm HIGH`, `450mm HIGH`, and `500mm HIGH`; preserve the project's established live-schedule convention rather than forcing a new global format.
- Do not derive damper type from this field.
- Missing/not applicable -> `-`.

### DAMPER TYPE

- Use explicit WIP/project/source value.
- Current template proves that a grille may have a cushion head while damper type is `OBD`, so the old rule `CUSHION HEAD present -> B/FLY @ DUCT` is invalid.
- `B/FLY @ DUCT`, `OBD`, or other values must be source/project-rule supported.
- Missing/not applicable -> `-`.

### SYSTEM

- Use explicit system reference from the WIP Lisp export, drawing context, or approved project mapping.
- **Do not derive SYSTEM from REF. NO. by string parsing as a default rule.**
- Current template has tags such as `E1`, `S1`, `R1` while SYSTEM is separately `EF-1`, `AC-2`, etc.; the tag alone is therefore insufficient.
- Missing unsupported system -> `-`.

### COMMENTS

- Preserve explicit project/drawing comments such as `REMOVABLE CORE` or `NECK ADAPTER`.
- Do not generate generic comments.
- Missing -> `-`.

## Formatting

- Preserve template column/header structure exactly.
- Text normalization should follow project convention; do not damage model codes.
- Use spaces around dimension separator in normalized human-readable values only when the live schedule convention requires it (for example `300 x 300`).
- Do not reorder dimensions unless their semantic axes are known.
- Never leave required schedule data cells blank; unsupported values use `-`.

## Exclusions

Exclude only when supported by explicit drawing/export/source classification or project rule:

- `BLANK-OFF` items;
- `DUMMY` items;
- loose accessories not intended as grille schedule rows;
- items outside the grille schedule definition.

Do not exclude a row solely because MAKE/MODEL/vendor data is missing.

## Audit and report

The primary drawing export has no required dated revision identifier.

For each grille run, record:

- `rule_status = draft`;
- actual WIP export path/filename;
- run timestamp;
- optional source content hash when deterministic tooling is implemented;
- optional `00 Input` technical-data revision(s), if used;
- added/updated/unchanged/review-required rows;
- conflicts and unresolved fields.

Do not create a synthetic `input_rev` for the Lisp export.

The human-readable report must repeat the `DRAFT / NOT FINAL` warning and summarize observations that may improve this rule.

## Validation checklist

Before considering a run complete:

- the current WIP grille export was explicitly/canonically resolved;
- template structure/order preserved;
- every schedule row originates from the current WIP drawing export or another explicitly approved project source;
- no invented MAKE/MODEL/system/color/damper values;
- AIR TYPE normalization is source/project-rule supported;
- design airflow, sizes and system values map from explicit source attributes;
- no automatic `ARCHITECT` color default unless project rule authorizes it;
- no automatic `B/FLY @ DUCT` derivation from cushion head;
- unsupported values are `-`;
- manual/enriched live values outside export ownership are preserved when required;
- audit/report identifies the current WIP export as primary source and optional technical data separately;
- draft warning remains visible.

7. project handling of damper type and cushion-head relationships;
