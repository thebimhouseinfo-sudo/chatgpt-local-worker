# Implementation Plan

## Objective
Describe the observable engineering objective and success condition.

## Inputs / Governing Architecture
Reference the relevant architecture sections, user decisions, specifications, issues, or repository evidence that constrain implementation.

## Constraints
List explicit technical, compatibility, platform, dependency, delivery, and user constraints.

## Non-Goals
List adjacent work intentionally excluded from this plan.

## Implementation Strategy
Describe the overall approach and why it fits the current architecture. Keep this at system/module level rather than line-by-line coding instructions.

## Phases
1. Describe an ordered implementation phase, affected subsystem(s), expected outcome, dependencies, and validation checkpoint.
2. Continue in dependency order.

## Migration / Compatibility
Describe schema/data/API migration, backward compatibility, rollout, fallback, or rollback requirements where relevant. Write `None` when not applicable.

## Validation Strategy
Define targeted checks first, then broader test/build/runtime/manual verification appropriate to the risk.

## Risks
List material implementation or operational risks and mitigations where known.

## Open Questions
List unresolved product/architecture decisions that must not be guessed by `dev-coding`. Write `None` when there are no material open questions.

## Task Mapping
Map phases to stable IDs in `TASKS.md` so a coding chat can select and execute work without re-planning the entire project.

## Handoff Notes
Record sequencing, environment, migration, rollout, or delivery notes that `dev-coding` must preserve.
