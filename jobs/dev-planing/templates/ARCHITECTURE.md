# Architecture

## Objective / Context
Describe the product/engineering context this architecture must support.

## Current Architecture
Summarize the current system boundaries, major components, data/control flow, persistence, integrations, deployment/runtime surfaces, and relevant repository evidence.

## Target Architecture
Describe the intended architecture after the planned work. Keep the description implementation-oriented and consistent with repository constraints.

## Boundaries & Responsibilities
List major modules/services/packages and what each owns. Call out interfaces that must remain stable.

## Data / State / Control Flow
Describe important data paths, state ownership, event/control flow, or lifecycle transitions affected by the work.

## Invariants & Constraints
List technical invariants, compatibility requirements, platform constraints, security boundaries, and decisions that implementation must preserve.

## Integration Points
List APIs, databases, queues, external services, file formats, build/deploy surfaces, or host integrations that matter to implementation.

## Architecture Decisions
Record settled decisions and the evidence/reasoning that makes them authoritative for implementation.

## Open Architecture Questions
List unresolved architecture/product decisions. Write `None` when no material question remains.

## Repository Evidence
Cite concrete files, symbols, tests, schemas, commands, docs, or history that support the architecture description.
